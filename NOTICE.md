This notice applies to the source code and build artifacts published in this repository. Features, permissions, storage locations and network behavior differ between runtimes; the defaults of one runtime must not be read as the project-wide settings.

## 1. AI Output, Execution Permissions and Automation Risks

AI-generated code, commands, explanations, files and suggestions may contain errors, omissions, security defects or third-party rights issues. Verify them against actual files, command exit statuses, tool results and tests; a model claiming something is "done", "handled safely" or "authorized" is not proof of fact or authorization. Before important operations, review the target, recipients and impact, and keep recoverable backups.

Files, terminals, Git, agent tools and external processes can read and write files, start processes and access the network within the permissions of the operating-system account that runs them. In Web or remote workspaces, operations may happen on the server, SSH host, WSL or container environment; do not infer the execution location from the device showing the page. The current shared agent execution adapter does not provide an OS sandbox by default; working directories, workspace identity, Git worktrees, browser page isolation and the Node REPL context are not system-level isolation guarantees for all tools.

Shared run configurations default to the `build` permission mode; when the standalone CLI runs a non-interactive task via `--prompt` without `--mode`, it uses `yolo`. Interactive sessions, desktop sessions, restored tasks and hosts may use their own configured, saved or passed modes. Whether each action is confirmed depends on tool declarations, permission rules and the run mode; `yolo` without a read-only planning constraint lets ordinary tool operations through, while interactive tools and tools that explicitly require confirmation keep their own rules. Model tool approval is not a single global permission switch for the entire app; terminal operations, plugin processes and update downloads must not be assumed to go through the same approval flow. See [CLI prompt modes](apps/zcode-cli/packages/cli/src/run.ts#L486) and [tool permission checks](apps/zcode-cli/packages/core/src/permission/service.ts#L97).

The standalone remote service core only accepts loopback listening addresses and does not provide equivalent external account authentication. HTTP/WS and HTTPS/WSS, and SSH, protect traffic under different conditions; not all deployments are guaranteed to be encrypted by default, and remote hosts or service operators are not guaranteed to be unable to access the data they process. ## 3. Local Data, Logs and Credentials

Data may be stored separately on the desktop device, in the browser, on the CLI host, in SSH/WSL environments and in external services. Desktop and server data directories can be affected by the runtime environment and startup configuration, and contain settings, sessions, attachments, caches, task records, plugins and logs; the standalone CLI's default session database is at `~/.zcode/cli/db/db.sqlite`. Closing a window, signing out, uninstalling the client or deleting one workspace should not be understood as clearing all copies in other environments, standalone data directories, backups and external services.

Memory features have different defaults and entry points: the standalone CLI's default configuration enables memory, while the desktop app's setting defaults to off. When enabled, it can analyze saved sessions, persist memories and reuse them in later tasks; extraction or organization may produce extra model requests. Automation schedules, run records and unfinished tasks also have their own persistence locations, and restoring these records does not guarantee previous external operations are undone or can be fully replayed.

Shared agent model input/output logs are written locally by default in development and production runs, except in test environments. Logs may contain prompts, code, context, tool arguments and model replies; headers and some image and video data are redacted, but not all user text can be assumed redacted. Production has rotation and trimming by default; explicitly enabling full retention changes that behavior. The desktop main process, host, scheduler, Web service and remote daemon also have their own logs and crash records; a single log cap does not mean a project-wide retention period.

Credential storage mechanisms also differ: the CLI shared credential file uses encryption, with a default key derivable from local environment information, and its read logic also accepts plaintext records; desktop/Node service credentials likewise use local encrypted files with configurable or environment-derived keys, not the system keychain; Web OAuth credentials may be stored in localStorage. Model configuration, environment variables, plugin/MCP settings, SSH configuration and remotely synced data may also contain valid credentials, and these stores should not be uniformly treated as a system keychain, hardware isolation or a "never leaves the device" guarantee.

The embedded browser uses persistent browsing data; explicitly importing cookies and LocalStorage from other browsers can give it the corresponding sign-in state. Clearing the cache and clearing all site data are different operations, and browser records, downloaded files, page recordings and model logs are not necessarily removed by the same cleanup entry. Do not write real keys or tokens into files tracked by version control. Before copying logs, uploading feedback, sharing conversations or backing up data directories, check the recipient scope to avoid submitting real credentials, raw sessions and private project content to public repositories or issue reports.
